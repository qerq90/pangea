# Pangea — Архитектурный документ

> **Назначение.** Это целевая архитектура и «полярная звезда» проекта Pangea. Документ нужен, чтобы (1) сверяться, идём ли мы в правильную сторону, и (2) дать контекст будущему ассистенту/ревьюеру, который подключится к проекту без истории обсуждений. Документ описывает **куда мы движемся** и **где находимся сейчас** — это разные вещи, и они явно разведены (см. раздел «Статус: текущее vs целевое»).
>
> **Заметка будущему Claude/ревьюеру.** Прежде чем предлагать изменения — прочитай раздел «Принятые решения и обоснования» и «Чего НЕ строим». Многие «очевидные» альтернативы (event sourcing, кодоген всех сцен, состояние в payload кнопки) уже рассмотрены и сознательно отклонены под конкретные боли. Не возвращай их без новой причины.

---

## 1. Что такое Pangea

Текстовая RPG в виде чат-бота. Игрок взаимодействует через кнопки и текстовые сообщения; бот отвечает сообщениями. Сейчас интерфейс — ВКонтакте, в коде уже заложен и Telegram. Игровой цикл: регистрация → выбор расы → подземелье/лабиринт → случайные события (находки, бой) → инвентарь, статы, прокачка.

По своей сути это **конечный автомат над графом сцен** с доменной механикой (генерация лута, бой, статы) и случайностью.

## 2. Технологический стек

| Слой | Технология |
|---|---|
| Язык | Scala |
| Эффекты/конкурентность | ZIO (`Task = ZIO[Any, Throwable, A]`) |
| БД | PostgreSQL |
| Доступ к БД | doobie |
| JSON | circe |
| Перечисления | enumeratum (+ `DoobieEnum`) |
| Миграции | goose (SQL) |

DI — через конструкторы + `ZLayer` (сервисы инжектятся как поля, **не** через ZIO-окружение `R`). Этой конвенции придерживаемся везде.

## 3. Принципы (полярная звезда)

Семь обязательств, по которым проверяется любое изменение:

1. **Движок в центре, интерфейс — адаптер.** Игровая логика не знает про ВК. ВК/Telegram/БД/тесты — сменные адаптеры вокруг ядра.
2. **Контент — данные, механика — код.** Тексты, кнопки, переходы описываются декларативно; код остаётся только там, где есть логика (эффекты, доменные вычисления).
3. **Functional core / imperative shell.** Доменные решения (бой, лут, статы) — чистые функции без IO. Эффекты-shell их оркеструют: загрузил → позвал ядро → сохранил → отрендерил.
4. **Детерминизм через явный RNG.** Случайность — это вход (seed), а не скрытый `new Random()`. Ядро воспроизводимо; роллы пишутся в журнал.
5. **Три вида состояния — три хранилища.** Durable game state, live scene state, append-only журнал не смешиваются.
6. **Надёжность чат-бота by construction.** Сериализация действий на игрока + идемпотентность апдейтов — структурно, а не «по соглашению».
7. **Граф валидируется на старте.** Битые переходы, недостижимые узлы, тупики ловятся при загрузке, не у игрока.

## 4. Слои архитектуры

Фактическая раскладка по пакетам (`core/src/main/scala/pangea/…`):

```
domain/      — Rng (чистый детерминированный генератор, без ZIO)
generator/   — чистое ядро: item/, loot/, monster/ (явный Rng на входе)
model/       — доменные модели: hero, item, monster, battle, trauma, stats, state…
engine/      — движок сцен + порты: Screen, Choice, Beat, Branch, Narrative,
               Target, SceneContent, GraphValidator, PartitionManager,
               Renderer, Players, Journal (порты живут здесь, не в отдельном ports/)
service/state/        — State, StateHandler, PlayerLock, UserAction + states/ (узлы графа)
service/sender/vk/    — адаптеры: VkApi, VkRenderer, VkPlayers
dao/ , repository/    — доступ к Postgres (включая dao/journal — JournalLive)
resources/scenes.yaml — контент сцен (тексты + кнопки) как данные
app/                  — Main (сборка ZLayer), server/ (вебхук-сервер ВК)
```

Зависимости направлены внутрь: адаптеры (`service/sender/vk`, `dao`) → порты (`engine`) ← `service/state` → `generator`/`domain`/`model`. Ядро ни от чего наружу не зависит. Отдельных пакетов `ports/`, `content/`, `adapters/` нет — порты лежат в `engine`, контент в `resources/scenes.yaml`, адаптеры в `service/sender` и `dao`.

### 4.1. Доменное ядро (`domain` / `generator`)

Чистые функции, без ZIO/IO, RNG передаётся явно как `domain.Rng`:

```scala
case class Rng(seed: Long) {
  def nextLong: (Long, Rng)
  def between(min: Long, max: Long): (Long, Rng)   // [min, max)
  def pick[A](list: List[A]): (A, Rng)
}

// generator/ — все принимают Rng и возвращают (результат, Rng)
ItemGenerator.createItem(lvl: Long, rarity: Rarity, rng: Rng): (Item, Rng)
LootGenerator.roll(tier, race, killLevel, rng: Rng): (List[LootDrop], Rng)
MonsterGenerator.generate(dungeonLevel: Int, rng: Rng): (Monster, Rng)
```

Тестируется property-тестами (`generator/*Spec`). Генераторы очищены от скрытого `Random` — `Rng` инжектится на вход.

`Rng` — линейный конгруэнтный генератор, а у него младшие биты ходят по короткому
кругу (самый младший — через шаг). Поэтому `between` перед делением с остатком
перемешивает биты (финал murmur3): иначе выбор из списка чётной длины повторял бы
чётность шага. Так было, пока в «тяжёлом» профиле не стало десять видов вещей:
оружие выпадало только на чётном шаге, и умение ему доставалось лишь из половины
списка. **Бой пока не вынесен в чистое ядро:** `BattleState` остаётся в shell и катает роллы через ZIO `Random` (см. §12).

### 4.2. Движок сцен (`engine`)

Платформо-независимое представление экрана и ввода построено и используется всеми сценами:

```scala
case class Screen(text: String, choices: List[Choice], inline: Boolean = false)
case class Choice(id: String, label: String, data: Map[String, String] = Map.empty,
                  color: ChoiceColor = ChoiceColor.Primary)
```

Ввод не вынесен в отдельный `sealed trait Input` — он приходит как `UserAction` (payload-кнопка или текст); `Branch` извлекает из payload ключ `action` и роутит. `Narrative` разворачивает цепочку `Beat`'ов в маршруты. Per-state матчей по enum'у `Action` на сцену больше нет: `Action`-энумы сохранились лишь как **кодеки payload-ключей** (строки в JSON кнопки), а диспетчеризацию ведёт `Branch` по строковому ключу.

**Цвет кнопки — данные, не код.** `ChoiceColor` (`Primary`/`Secondary`/`Negative`/`Positive`) задаётся **в yaml на самой кнопке**, дефолт `Primary`; `VkRenderer.toButtonColor` маппит его в `ButtonColor` (negative = красный). В yaml кнопка — либо `id: "label"` (→ primary), либо `id: { label: "...", color: "negative" }`. Динамические кнопки, собираемые в коде, тоже берут метку **и** цвет из yaml-ключа через `content.choice(id, key, args*)` (id — это action; метка/цвет — из данных). Цвет нигде не выводится по эвристике из текста метки — только явный параметр. Кнопки-«отступления» (Уйти/Назад/Оставить/Сбежать и т.п.) помечены `negative`.

### 4.3. Порты и адаптеры (`engine` / `service/sender/vk`)

Порты объявлены в `engine`, реализации — в адаптерах:

```scala
trait Renderer { def show(user: User, screen: Screen): Task[Unit] } // VkRenderer
trait Players  { def getDisplayName(user: User): Task[String] }      // VkPlayers
trait Journal  { def append(event: GameEvent): Task[Unit] }          // JournalLive
```

`VkRenderer` превращает `Screen` в сообщение ВК с клавиатурой; `VkApi` парсит входящий апдейт в `UserAction`. Флаг `Screen.inline` управляет видом клавиатуры: `false` (по умолчанию) — обычная клавиатура снизу, `true` — inline-кнопки внутри самого сообщения (`Keyboard.withInline`); используется на экране добычи (`LootState`). `Screen.image` — картинка к сообщению: ссылка на фото из альбома группы ВК (`photo-<группа>_<фото>` или полный адрес фото). `VkRenderer` отдаёт её вложением (`Attachment.parse`), и ВК прикрепляет уже загруженное фото — заново его не грузим. Первое применение — фото лабиринта к «Исследовать уровень»: список `dungeon.explorePhotos` в `scenes.yaml`, каждый раз случайное фото (`DungeonState.explorePhoto`, по миллисекунде нажатия, чтобы не сдвигать броски событий). Сцены работают только через `Renderer`/`Screen` — `Keyboard`/`sendMessage` из них убраны, ВК больше не протекает в стейты. Telegram пока заглушка: `StateHandler.makeActionTelegram` есть, но отдельного рендерера/вебхука нет (использует `VkRenderer`).

## 5. Модель сцены

Узел графа — один из трёх видов:

- **Нарратив** — текст + одна кнопка «дальше» → следующий узел. (Линейные катсцены, как цепочка Travel в регистрации.)
- **Выбор** — текст + несколько кнопок, каждая ведёт в свою цель.
- **Эффект** — выполняет код и по результату выбирает следующий узел.

Цель кнопки (`Target`) — либо данные, либо код:

```scala
sealed trait Target
object Target {
  case class Goto(state: StateType)                                  extends Target // данные → ключ сцены
  case class Run(f: (User, UserAction, Renderer) => Task[StateType]) extends Target // код (эффект)
}
```

`Branch(routes: Map[String, Target], fallback: Target)` маршрутизирует по строковому ключу `action` из payload кнопки; `gotoTargets` отдаёт все `Goto`-цели для валидатора графа.

**Граница данные/код проходит по `Target`.** `Goto` сериализуем (держит ключ сцены), `Run` несёт функцию (эффект — всегда код). Сцена — «в основном данные с явными дырками под код».

**Правила для эффектов:**
- Сервисы (api, dao, repo) **захватываются** (эффект — метод стейта с этими полями), а не передаются в сигнатуру.
- В shell остаётся оркестрация (вызвать ядро, сохранить, отрендерить, выбрать следующую сцену) — это его законная работа, её не «прячут».
- Хелпера `Run.decoded[A]` (декод payload в доменный тип на границе) пока нет — эффекты, которым нужен payload (напр. выбор расы), читают `ua.payload` внутри себя. Это кандидат на будущее упрощение.

## 6. Модель состояния

| Вид | Что | Хранилище | Жизненный цикл |
|---|---|---|---|
| **Durable game state** | статы, инвентарь, прогресс | мутабельные таблицы (`heroes`, `inventory`) | источник истины |
| **Live scene state** | текущая сцена + scratchpad (выкаченный предмет до клика) | одна колонка-блоб на герое (`scene_data JSONB`) | перезаписывается следующей сценой |
| **Журнал** | что произошло (роллы, исходы, ошибки) | append-only таблица, партиционированная | retention-окно |

**Payload кнопки несёт только ссылку** (какая сцена / какой выбор), не состояние. У ВК payload ограничен по размеру; состояние живёт на сервере (live scene state), в кнопке — крошечный идентификатор.

Инвариант «ровно одно живое состояние на игрока» гарантирован **структурно** (одна колонка одной строки героя), а не соглашением.

### Экран = отдельное состояние (`State`)

Каждая локация/экран со своими кнопками — это **отдельный `StateType` + отдельный класс-`State`** (свой файл), переход — через `Target.Goto`, «Вернуться» — `Goto` обратно. Эталон — `MerchantState`; так же сделаны таверна и её под-локации (`TavernState`, `InnkeeperState`, `MercenariesState`, `CardSellerState` в `service/state/states/tavern/`) и гильдия (`GuildState`, `QuestBoardState`, `TrophyExchangeState`, `TrainingHallState` и др. в `service/state/states/guild/`).

**Чего НЕ делать:** дописывать новый экран inline-методами (`showX`/`renderX`) внутрь чужого `State` и роутить его действия через тот же `Branch`. Так раньше были «таверна/комната/уличные торговцы» внутри `GlobalMapState` — узел разросся в свалку, а «вернуться на экран X» оказалось невозможно сделать через `Goto` (экрана-состояния не существовало). Если у экрана есть свои кнопки и переходы — заводи `StateType`, класс-`State` и регистрируй в `StatesMap` (граф проверит `GraphValidator`). Это прямое следствие принципов §3.2 (контент — данные) и валидируемости графа §3.7.

## 7. Детерминизм и RNG

Игра полна случайности (`rollLoot`, выбор события, бой). RNG — инжектируемый seed на вход чистого ядра. Это даёт:
- тестируемость ядра без моков;
- воспроизводимость багов: seed и реальные роллы пишутся в журнал → сессию можно переиграть как было.

Запрет: скрытые `new Random()` внутри доменной логики.

## 8. Надёжность чат-бота

> **Статус: ✅ реализовано.** Чат-платформы передоставляют сообщения, игроки жмут дважды, апдейты приходят внахлёст. Решено структурно:

- **Сериализация по игроку.** `PlayerLock` — `Ref[Map[VkId, Semaphore]]`, по семафору на игрока (`withLock`). `StateHandler.makeActionVK` оборачивает всю обработку апдейта в `lock.withLock(vkId)` → переходы упорядочены, не гоняются. By construction убивает класс «два конкурентных перехода».
- **Идемпотентность.** Апдейт несёт `eventId`; `userRepo.checkAndRecordEvent` атомарно пишет `users.last_event_id` через `UPDATE … WHERE last_event_id IS NULL OR last_event_id <> $eventId` и возвращает, новый ли это апдейт. Повтор того же `eventId` → `isNew = false`, обработка пропускается. Дабл-тап не ломает стейт.

## 9. Журнал и партиционирование

> **Статус: ✅ реализовано.** Порт `engine.Journal` + `dao/journal/JournalLive` пишут в партиционированную `event_log` (миграция `20260617000000_event_log.sql`). `engine.PartitionManager.ensurePartitions` нарезает партиции на 3 месяца вперёд при старте `JournalLive`. `GameEvent` пишется в ключевых точках: `race_selected` (Registration), `item_found`/`item_left` (FoundItem), `loot_claimed` (Loot). Старая `events`-таблица как live-state выведена из обращения — live-состояние теперь в `heroes.scene_data`.

Журнал — **append-only**: только `INSERT`, никаких `status`/`UPDATE`/`.unique`. Строка — это факт, который случился.

```sql
CREATE TABLE event_log (
    id BIGSERIAL, user_id BIGINT NOT NULL,
    event_type VARCHAR(64) NOT NULL, payload JSONB NOT NULL,
    trace_id UUID, occurred_at TIMESTAMP NOT NULL DEFAULT now(),
    PRIMARY KEY (id, occurred_at)          -- ключ партиции обязан входить в PK
) PARTITION BY RANGE (occurred_at);
```

- Партиции по месяцу; `DEFAULT`-партиция как предохранитель; нарезка на пару месяцев вперёд.
- Ретеншн = `DROP TABLE` старой партиции (мгновенно), а не `DELETE`.
- Обслуживание: **pg_partman (+pg_cron)**, если хостинг даёт расширения; иначе ZIO-джоб «создать вперёд / дропнуть старое». Решает доступность расширений на сервере.
- `trace_id` связывает строки одного действия в цепочку.
- Запросы — с границей по `occurred_at`, иначе нет partition pruning.

Логировать стоит **роллы и исходы** (что выкатил генератор, влез ли предмет, что выбрал игрок, ошибки) — то, что иначе не восстановить.

## 10. Жизненный цикл апдейта

1. ВК-вебхук → адаптер парсит в `Update(playerId, Input)`.
2. Диспетчер отдаёт в **сериализованный по игроку** обработчик.
3. Загрузка игрока (durable + текущая сцена + scratchpad).
4. Глобальная команда (`/home`, `/stats`, `/restart`) → обработать; иначе `Tap` → найти выбор в текущей сцене → выполнить `Target` (`Goto`/эффект).
   `/restart` идёт в два шага: сама команда лишь показывает предупреждение с inline-кнопкой (клавиатура сцены остаётся), и только её нажатие стирает героя со всем, что к нему привязано (`Queries.deleteHeroCascade`), — запись `users` и журналы остаются, а следующее же действие заводит нового героя и начинает регистрацию.
5. Эффект: вызовы ядра + персист + `journal.append`, возвращает следующую сцену.
6. Рендер сцены через `Renderer` → ВК-адаптер шлёт сообщение.
7. Сохранить позицию + scratchpad; пометить апдейт обработанным.

## 11. Тестирование

- **Ядро** — property-тесты (инварианты боя/лута/статов).
- **Граф сцен** — headless-драйвер: «бот-игрок» ходит по графу через `Input`/`Screen` без ВК; целые нарративные ветки проверяются юнит-тестами.
- **Журнал** — проверка, что в ключевых точках падают правильные события.
- **Старт** — валидатор графа как тест: нет битых переходов/недостижимых узлов.

## 15. Чего НЕ строим (YAGNI)

- **Event sourcing.** Журнал наблюдательный; истина — в мутабельных `heroes`/`inventory`. Полный ES — оверкилл.
- **Микросервисы.** Один сервис + Postgres держит большую аудиторию.
- **Свой DSL контента на старте.** Сначала данные (HOCON/ресурсы) + валидатор; DSL — когда заболит.
- **Распределённая сериализация игроков.** Внутрипроцессной хватит, пока не упрёшься.
- **Кодоген всего.** Целевой путь для flow — интерпретатор сцен (`Branch`/`Narrative`), а не генерация Scala. Временный кодоген клавиатур (`kbgen`) в проекте отсутствует.

## 16. Боевая механика и формулы

### Урон игрока
```
damage = (atk + str) × spread / 100 × weaponMod × closeMod
```
- `atk` — `fightStats.atk`, растёт от оружия и баффов
- `str` — `baseStats.str`, растёт от прокачки
- `spread` — равномерное случайное значение 80–120 (разброс ±20%)
- `weaponMod` — 0.5 без оружия (обе руки пусты), 1.0 с оружием
- `closeMod` — 0.8, когда из лука или арбалета бьют вблизи (по тому, кто напротив, и по соседям), иначе 1.0 (`BattleState.rangedCloseMod`)

**Важно:** формула аддитивна (`atk + str`), не мультипликативна. Умножение (`atk × str`) давало квадратичный рост и было исправлено.

### Броня
```
maxArmor          = ⌊allArmor × max(defence / 2, 1)⌋
effectiveMaxArmor = ⌊allArmor × (1 − armorPct) × max(defence × (1 − defPct) / 2, 1)⌋   // с травмами
```
- `equipment.allArmor` — сумма `armor` всех надетых предметов
- `defence` влияет на броню **вдвое слабее** (множитель `defence / 2`); множитель **зажат снизу единицей** (`max(…, 1)`), поэтому при `defence ≤ 2` броня работает без вложений в защиту, а защита в множителе никогда не ниже 1
- В бою броня поглощает урон первой и расходуется; на отдыхе/лечении восстанавливается до **`effectiveMaxArmor`** (`RestState`; в комнате таверны, `TavernState`, травмы снимаются, поэтому там до полного `maxArmor`)
- **Травма режет ПОТОЛОК брони (`effectiveMaxArmor`), а не текущий запас.** `fightStats.armor` — текущая броня; в бою она тратится ровно на поглощённый урон (`current − absorbed`), без повторного применения `armorPct`. Раньше бой брал `effectiveFightStats.armor = armor × (1 − armorPct)` и сохранял это обратно — травма «съедала» часть запаса при первом ударе и компаундилась (баг: `240/240` → удар на 20 → `160/240`). Теперь `effectiveFightStats.armor` равен текущему запасу без штрафа; штраф живёт только в `effectiveMaxArmor`
- Показ (боевой экран и «Персонаж») — `min(current, effectiveMaxArmor) / effectiveMaxArmor`
- Пересчёт `fightStats` при надевании/снятии экипировки (`InventoryState.applyDelta`) зажимает каждую характеристику (`atk`, `armor`, `defence`, `evasion`, `accuracy`, `concentration`) в `.max(0L)` — снятие предмета не уводит текущие значения в минус

### Предметы и их ID
Каждый предмет получает реальный `BIGSERIAL` ID в таблице `items` **в момент генерации** (через `ItemRepository.generate` / `ItemRepository.persist`), до попадания в инвентарь. В JSON-блобе инвентаря и слотах экипировки хранится предмет с уже настоящим ID. Это гарантирует уникальность при `removeItem`.

### Обязательные прибавки оружия и доспеха

После генерации статов `ItemGenerator.applyMandatory` накладывает гарантированный бонус по типу предмета (R1 = `rarity.factorR1`):

- **Оружие** (`ItemType.Weapon`) — к атаке `lvl × (5 + R1) ±20%` (поверх обычных статов). Прибавляется к полю `Item.attack`, поэтому учитывается обычным `applyDelta` при надевании.
- **Нагрудник** (`ItemType.ChestPlate`) — к максимуму HP персонажа `lvl × (12 + R1) ±10%`. Кладётся в новое поле `Item.hp`; `Equipment.allHp` суммирует HP экипировки, а `Hero.effectiveMaxHp` прибавляет его (плоско, поверх трав­мо-модифицированной базы от телосложения). `Item.hp` показывается в списках предметов как `HP +N`.

### Отдых
После истечения `restDurationMs` (30 с — обычный, настраивается `DeathState`) восстанавливаются:
- HP до `effectiveMaxHp` (`vit × 24 × raceFactor`)
- Броня до `maxArmor`

### Боевой экран
Во время боя игроку показывается:
```
⚔ <Редкость Раса>
Раса: <раса>
❤ <текущий>/<макс> | 🧥 <броня>/<макс> | ⚔ <урон>
🎯 Попадание: <шанс попасть по игроку>% | 💨 Уворот: <шанс увернуться от игрока>%

🧙 Вы: ❤ <текущий>/<макс> 🧥 <броня>/<макс>
🧪 Фляга: <заряды>
```
- **Попадание** — вероятность, что моб попадёт по игроку = `100 − playerDodge` (см. ниже), зажато в [5%, 95%]
- **Уворот** — вероятность, с которой моб уйдёт от удара игрока = `mobDodge` (та же формула уклонения); зажато в [5%, 95%]
- Оба числа считаются из **эффективных** характеристик героя (с учётом баффов/дебаффов раунда)
- Броня показывается как `текущая/максимальная` и для моба, и для героя

### Модификаторы мобов

Общий механизм усиления, накладывается при генерации (`MonsterGenerator.generate`).

- **«Отмеченный тьмой»** — **5% шанс** на любого моба. Все показатели ×1.2 (`MonsterMultiplier = 1.2`), к имени спереди добавляется `Отмеченный тьмой` (`Monster.MarkedPrefix`). Флаг `Monster.marked` несёт это; он сохраняется в бою (`ActiveBattle.monsterMarked`, обратносовместимый декод через `getOrElse(false)`), поэтому префикс держится весь бой. Усиленные статы уже зашиты в `monsterStats`.

#### Попадание по юниту — единая формула уклонения (`dodgeChance`)

Шанс попадания по любому юниту считается **одинаково для обеих сторон**: атакующий попадает, если бросок `1..100` **больше** уклонения защищающегося. Уклонение:
```
dodgeChance = 100 × (agi + evasion) / (agi + evasion + defence × 1 + attackerAccuracy × 3)
```
зажато в **[5, 95]** (проценты).
- Положительные параметры (числитель): ловкость `agi` и уклонение `evasion` **защищающегося**
- Отрицательные (знаменатель): защита `defence` защищающегося (×1) и точность `accuracy` **атакующего** (×3). Вес был 1.5: его подняли вдвое, а точность на новых вещах и у мобов вдвое срезали — попадания те же, а урон умений от точности меньше
- `BattleState.dodgeChance(agi, evasion, defence, attackerAccuracy)` — единственная функция:
  - **уклонение игрока** от удара моба: `dodgeChance(heroAgi, heroEvasion, heroDefence, monsterAccuracy)`
  - **уклонение моба** от удара игрока: `dodgeChance(0, monsterEvasion, monsterDefence, heroAccuracy)` — у моба нет ловкости (`agi = 0`)
- Заменил прежние раздельные `mobHitChance` (`monsterAccuracy / (agi×2.5 + evasion)`) и `playerHitChance` (`accuracy / monsterEvasion`)

### Фляга

Фляга — особый предмет (`ItemType.Flask`). Разные фляги выпадают с разными эффектами и запасом зарядов; логика эффекта закодирована прямо на предмете.

**Модель:**
```
Item.flaskEffect: Option[FlaskEffect]   // эффект при употреблении
Item.charges:     Option[Int]           // текущие заряды
Item.maxCharges:  Option[Int]           // максимум зарядов
```

**Эффекты (`FlaskEffect`):**
| Тип | Описание |
|-----|----------|
| `HealPercent(percent)` | восстанавливает `max(maxHp × percent / 100, 1)` HP |
| `AddBuff(buff, rounds)` | добавляет боевой бафф на `rounds` ходов |

**Правила боя:**
- Фляга должна быть экипирована в слот flask; без экипировки UseFlask возвращает ошибку
- **Один раз за раунд** — повторное нажатие заблокировано флагом `ActiveBattle.flaskUsedThisRound`; он сбрасывается в `tickBuffs`, который вызывается когда моб атакует в ответ на удар игрока
- Моб **не** наносит ответный удар — фляга бесплатное действие внутри хода

**Пополнение зарядов:**
- У источника воды (`DungeonState.healAtSpring`) восстанавливаются до `maxCharges` экипированная фляга и все фляги в инвентаре (`InventoryRepository.refillFlasks`)
- Стартовая фляга — фляга целителя на поясе из тайника в сторожке (`RegistrationState.kit`): белая, на четыре глотка, полная

### Пул событий лабиринта

«Искать» (`FindEvent`) тянет билет из пула `StateType.events`: сто билетов, у события их
столько, каков его вес (бой 37, находка 19, ручей 18, жила 9, раскопки 5, мобы с сокровищем 5,
поляна 2, девушка 2, пещера 1, караван 1, логово элементаля 1). «Охотник» и «Скрытность»
меняют число билетов боя (`eventsWithBattleFactor`).

События открываются по мере спуска (`StateType.EventMinLevel`, пул уровня — `eventsAt`):
- с 1-го — бой, находка, ручей, жила, раскопки, поляна;
- с 5-го — групповые бои: девушка и мобы с сокровищем;
- с 7-го — логово элементаля;
- с 10-го — пещера с монстрами и караван.

Считается текущий уровень лабиринта (`dungeonLevel`). У закрытого события в пуле нет
билетов, поэтому выше доли остальных больше: на 1–4 уровнях в пуле 90 билетов, бой — 41%.
Расплата рас, банда, приговор и зовы волка и Джо идут мимо пула и от уровня не зависят.

Внутри событий есть порог по уровню **героя**: Белый волк на поляне и Гнилой Джо на
раскопках сами выходят к герою только с 4-го уровня (`MiniBoss.AmbushMinHeroLvl`).
Младшему на поляне волк не попадается, а доля Джо на раскопках уходит «свежей могиле».
Позвать их отваром или узелком можно с любого уровня.

### Огонь и холод

Огонь и холод гасят друг друга — на мобе, минибоссе и на герое:
- холод по горящему гасит пламя и сам не ложится;
- огонь по цели под холодом (срез защиты, у огненного элементаля — оцепенение)
  растапливает лёд и сам не занимается;
- сработали оба в одном ударе (рубин и сапфир в оружии) — гасят друг друга, на цели
  ничего не меняется.

У мобов это проки стихий оружия и фляг (`applyProcs`), у героя — поджог и морозный
удар моба, шипы и всплеск огненного элементаля. О каждом таком случае — строка в
логе (`battle.elements.*`).

### Событие «Ручеёк» (Spring)

- HP полностью восстанавливается до `effectiveMaxHp`
- Все фляги (в слоте и в инвентаре) пополняются до `maxCharges`
- **50% шанс засады**: после лечения бросается `Random.nextIntBetween(1, 101)`; при результате ≤ 50 — немедленно стартует бой (`startBattle`), игроку показывается сообщение «Однако на шум живительного ручья пришёл и кто-то ещё…»

## 17. Опыт и уровни

### Модель

`hero.exp` хранит опыт **внутри текущего уровня** — не суммарный накопленный. При достижении порога уровня exp сбрасывается в 0, уровень растёт.

```
neededExp(lvl) = 100 × fib(lvl)   // fib(1)=1, fib(2)=2, fib(n)=fib(n-1)+fib(n-2)
                                  // → 100, 200, 300, 500, 800, 1300, …
```

`Hero.neededExpForLevel(lvl)` — единый источник порога (использует и `getNeededExp`, и level-up). Отображение: `exp / neededExp` (например, `37/100` на уровне 1).

### Level-up

Происходит в `BattleState.victory` через цикл, который обрабатывает несколько уровней за раз:

```scala
while (exp >= Hero.neededExpForLevel(lvl) && lvl < 150L) {
  exp  -= Hero.neededExpForLevel(lvl)
  lvl  += 1L
  upgradePoints += 4L
}
```

Каждый новый уровень даёт **+4 очка прокачки**. Максимальный уровень — 150.

### Смерть и опыт

Смерть **не снижает уровень**. Теряется 10% опыта внутри текущего уровня (`(exp × 0.1).max(0)`), уровень и очки прокачки остаются неизменными. Дыра «умереть на пороге уровня ради двойных очков» закрыта этой моделью: уровень не откатывается, повторно получить очки за тот же уровень невозможно.

## 18. Механика смерти

Смерть наступает в `BattleState`, когда HP героя падает до 0. Переход: `StateType.Battle → StateType.Death → StateType.Rest`.

**Состояния без пользовательского взаимодействия.** Состояние может полностью отыграться в `enter` и сразу перейти дальше, не требуя нажатия кнопки. Это даёт общий механизм `State.autoAdvance: Option[StateType]`: если игроку нечего решать, состояние указывает следующее, а `StateHandler.transitionTo` чейнит переход (persist + `enter`) без действия игрока. Цикл авто-переходов ограничен предохранителем (fuel); обычные узлы-выборы оставляют `autoAdvance = None`.

`Death` — **пример такого узла-эффекта**: его `enter` сразу начисляет штрафы, выбирает травму, роняет предметы и пишет `restDurationMs`, после чего через `autoAdvance = Some(Rest)` без кнопки «Продолжить» уходит в `Rest`.

### Штрафы при смерти

| Параметр | Формула |
|---|---|
| Опыт | −10% опыта **внутри текущего уровня** (`exp × 0.1`, min 0); уровень не снижается |
| Серебро | −50% (`silver / 2`) |
| Травма | случайная из текущего тира (см. ниже); добавляется к списку активных травм |

### Механика травм

Каждая смерть добавляет **одну** новую травму. Травмы **накапливаются списком** и действуют одновременно, их штрафы суммируются по каждому стату. Таймер 8 часов от **последней смерти** сбрасывается при каждой смерти; когда он истекает — весь список обнуляется разом.

**Прогрессия по тирам:** пока не собраны все 4 лёгкие → выпадают только лёгкие; потом только средние (пока не собраны все 4); потом только тяжёлые.

**Максимум травм.** Когда собраны все травмы всех тиров (пул новых пуст), новая травма **не выдаётся**: список не растёт, но таймер снятия всё равно продлевается на 8 часов от текущей смерти, и показывается сообщение «На вас не осталось живого места..» (`death.traumaMax`). Реализовано в `DeathState.applyTrauma`: при `pool.isEmpty` — только `updateTrauma(Some(traumaUntil), existingNames)` + сообщение.

#### Лёгкие травмы

| Травма | Штрафы |
|---|---|
| Ушиб ноги | −5% уклонение |
| Раздробленный палец | −5% урон, −5% сила |
| Ноющее ребро | −5% HP, −5% телосложение |
| Порванное ухо | −5% точность, −5% сосредоточение |

#### Средние травмы

| Травма | Штрафы |
|---|---|
| Порезанное ахиллесово сухожилие | −25% уклонение, −15% броня, −15% защита |
| Проколотая рука | −25% урон, −25% сила |
| Глубокий порез живота | −25% HP, −25% телосложение, −15% броня, −15% защита |
| Сломанный нос | −25% точность, −25% сосредоточение |

#### Тяжёлые травмы

| Травма | Штрафы |
|---|---|
| Повреждение коленной чашечки | −50% уклонение, −15% броня, −15% защита |
| Сломанная рука | −50% урон, −50% сила |
| Глубокий разрез правого бока | −50% HP, −50% телосложение |
| Расколотый череп | −50% точность, −50% сосредоточение, −75% интеллект |

**Хранение:** `heroes.trauma_names TEXT` (имена через запятую) + `heroes.trauma_until BIGINT`. Список активных травм читается через `Hero.activeTraumas(nowMs)`, суммарный штраф — через `Hero.combinedPenalties(nowMs)`. Штрафы применяются к каждому стату независимо в `effectiveFightStats` и `effectiveMaxHp`. Снятие — в таверне (см. ниже), обнуляет оба поля.

### Таверна «Золотой якорь» (`TavernState`)

Таверна — **отдельное состояние** `StateType.Tavern` (`service/state/states/tavern/TavernState.scala`), переход из города `GlobalMap --Goto--> Tavern`, выход `LeaveTavern --Goto--> GlobalMap`. Меню (`tavern.menu`): «Снять комнату», «Трактирщик» (`--Goto--> Innkeeper`), «Наёмники» (`--Goto--> Mercenaries`), «Персонаж», «Уйти». Раз в час катается «Подозрительный человек» (`CardSeller.rollAndLoad`): пока он здесь, над «Персонажем» висит его кнопка (`--Goto--> CardSeller`). Трактирщик, наёмники и продавец карт — самостоятельные состояния (по образцу `MerchantState`), их «Вернуться» делает `Goto(Tavern)`. Доска заданий висит не здесь, а в Гильдии искателей (см. «Доска заданий»).

**Снятие комнаты.** Стоимость привязана к **уровню героя**: `roomCost = max(lvl × 10, 10)`, платится из кошеля (`Purse`: своё серебро, следом — ячейка Торгового дома). Время старта хранится в `scene_data` (`tavernRoomStartedAt`):

- **Снять комнату** (`RentRoom`) — списывает серебро, пишет время старта, ставит задачу `TaskKind.TavernHeal` на 3 часа вперёд и показывает комнату («Вы сняли комнату… Через 3 часа все травмы пропадут») с кнопкой «Уйти».
- **Уйти** (`LeaveRoom`; через 3 часа его выполнит сам поллер, если герой всё ещё в таверне):
  - прошло **≥ 3 часов** → лечит травмы (`updateTrauma(None, Nil)`), восстанавливает HP, броню и энергию до полного, отряд отсыпается (`squad.restored`), «Ваши травмы успешно излечены…», возврат в меню таверны;
  - **раньше** → подтверждение «До исцеления от травм осталось N, вы уверены?» с «Да»/«Нет». «Да» (`ConfirmLeaveRoom`) — прерывает без исцеления (серебро не возвращается), «Нет» (`CancelLeaveRoom`) — обратно в комнату.
- Повторный заход в таверну при активной комнате (`scene_data` содержит ключ) сразу показывает комнату, а не предложение снять. Уход в подземелье перезаписывает `scene_data` и аннулирует комнату (серебро потеряно).

### Пробуждение и задание «Встать на ноги»

После портала и выбора расы (`RegistrationState`) герой падает на соломенную крышу
сторожки посреди лабиринта — биты `registration.arrival`, отдельно от пролога:
- **Обыск** (`ArrivalSearch`) выдаёт тайник искателя (`RegistrationState.kit`): всё
  белое, первого уровня, статы как у обычной добычи. Меч и Круглый Щит — в руки,
  пояс с флягой целителя на четыре глотка — на себя, Двуручный Топор и поровну Лук или
  Арбалет — в сумку. Что из стрелкового выпало, помнит `kitRanged` в scene_data: по нему
  сцена обыска и при повторе называет то, что лежит в сумке.
  Выдаётся один раз: отметка `kitFound` в scene_data.
- Три монолога, и **«Встать»** (`ArrivalStand`) ставит задание и уводит в лабиринт.

Задание «Встать на ноги» (`FirstSteps`) герой ставит себе сам; взятым его отмечает
`LoreData.firstSteps`. Пункты считаются по тому, что уже есть у героя, — копить для
задания ничего не нужно (`FirstSteps.progress`, вывод — `FirstStepsQuest`):
- окрепнуть — 5-й уровень;
- обзавестись логовом — купить дом (домов пока нет, пункт ждёт их);
- разведать город — вступительные задания горожан: Трактирщик, Ришелье, Густаво,
  Жрец, Мастер Горн (`FirstSteps.CityQuests`).

### Журнал заданий («📜 Задания» в «Персонаже»)

Кнопка `OpenQuests` в `HeroStatsState` присылает одним сообщением всё, что у героя в
работе (`QuestJournal`), — под ним остаются кнопки «Персонажа». Журнал только читает:
- «Встать на ноги», если взято и не закрыто, — с пунктами (`FirstStepsQuest`);
- задания горожан на своём шаге: название и что делать сейчас, со счётчиком, где он
  есть (`journal.quests.<ключ>`: `title` и `steps` по порядку шагов). Вскрытое письмо
  Марисе подсказывает и путь по карте;
- сегодняшние поручения, взятые и не сданные, — репликой горожанина `active`/`ready`;
- взятые объявления доски этой недели — тем же «что просят», что и на доске
  (`QuestBoardState.ask`), с пометкой «в работе» или «сделано, можно сдавать».

### Вещи для поручений: сумка и артефакты (`QuestGoods`)

Камни сами ложатся в Ларец Азата, травы и отвары — в Живую сумку (`ArtifactKind.autoCollect`).
Поэтому то, что горожанин просит принести или показать, ищется и там:
- поручения «принеси» (`DailyDialog.give`): Густаво — травы, Рахадим — надколотый камень;
- задание Жреца «То, что не пропадает»: камень можно показать и из Ларца.

`QuestGoods.all` отдаёт сперва сумку, потом артефакты, поэтому при равных вещах отдаётся
сперва из сумки. `QuestGoods.remove` забирает отданное оттуда, где оно лежало. Миниатюрный
шкаф не в счёт: что в нём лежит, хозяин убрал сам.

Продажа трав у Густаво: «Сдать всё» (`HerbsSell`) берёт травы только из сумки, а травы из
Живой сумки идут отдельным списком и своей кнопкой «Сдать из Живой сумки» (`HerbsSellLiving`).
Отвары остаются в ней. Когда трава есть и там, и там, обычная кнопка подписана «Сдать из
сумки».

### Доска заданий (`QuestBoardState`)

Доска висит в Гильдии искателей (`BackFromQuest --Goto--> Guild`). Гильдия держит по доске на
каждые 25 уровней (`BoardTier`: 1–25 … 126–150), стена (`questBoard.wall`) показывает все:
- открыты своя и предыдущая (`BoardTier.open`): 26-й берёт и с 1–25, и с 26–50, 51-й — с 26–50
  и 51–75; у новичков предыдущей нет;
- к старшим не пускают, у каждой свой отказ (`questBoard.locked.<ключ>`);
- на младших, ниже предыдущей, отвечают «дай молодым дорогу» (`questBoard.tooOld`).

Состояние durable в `heroes.quest_data` — стол `BoardDesk`: у каждой доски (`BoardData`: неделя,
раздел, объявления) свои 8 мест (`BoardRates.Slots`) и своя неделя. Запись прежнего вида — одна
доска без обёртки — читается как стол с этой доской. При заходе на доску (`load`) со стола
уходят прошлонедельные и уже не открытые герою доски (`BoardDesk.fresh`), а недостающая
роллится заново (`QuestBoardState.roll`). В понедельник в 00:00 МСК (`BoardRates.weekOf`) доска
переписывается целиком: взятое и не сданное сгорает, неделя и есть срок.

Что на доске: у новичков всегда три трофея названных рас, остальные места — из пула
(`BoardRates.Pool`: караван, пещера, канализация, воры, гномьи припасы, некромант), каждый вид не
больше раза; старшие доски целиком из пула. У выездных (`BoardKind.away`: воры, канализация,
некромант) уровень свой, в пределах раздела.

- **Взять** (`BoardTake_<раздел>_<номер>`) — хоть все объявления с обеих досок. С выездным
  герой сразу уходит в дорогу (`QuestRoad`, `RoadProgress` в scene_data); ушёл, не доделав, —
  кнопка «Идти» (`BoardGo_…`) ведёт туда снова.
- Дела, что отмечаются в пути (всё, кроме `BoardKind.handedIn`), отмечает `BoardProgress` —
  на той доске, где они взяты (`BoardDesk.markDone`/`markFailed`). Поэтому одно и то же такое
  дело на двух досках разом не берут (`questBoard.sameKindTaken`).
- **Сдать** (`BoardHand_…`) — трофей (`BoardTrophy.bestFor`) и ящик из 10 склянок гномам
  (`handedIn`) уходят из сумки, ларца или живой сумки (`QuestStash`); за отмеченное платят
  опытом `BoardRates.exp` и дублонами. Сданное объявление уходит с доски.
- Кнопки со старых экранов без раздела (`BoardTake_<номер>`, `BoardMine`) ведут на свою доску,
  а раздел, который уже не открыт, — к стене.

### Трактирщик (`InnkeeperState`)

Под-локация таверны. Трофеи доски он не принимает — их сдают на доске в Гильдии. Кнопки
появляются по тому, что у героя сейчас есть:
- **«Плата за первую кружку»** (`NpcQuest.Innkeeper`, через `NpcQuestDialog`) — вступительное
  задание: принести любой трофей. Трактирщик забирает самый дешёвый (`cheapestTrophy`: меньший
  коэффициент вида, при равных — младший), платит 100 серебра (`QuestSilver`) и опыт, а после
  рассказывает о Кинэте (`KinetLore`) — уже бесплатно.
- **Рассказы о боссах** за серебро, по разу, после встречи с ними: элементали — 2000, Гнилой
  Джо — 1000, Белый волк — 1500, Крысиный король — 1000 (`InnkeeperState.*LorePrice`, отметки
  в `LoreData`). Про Некроманта не рассказывает: отправляет к Жрецу (`necroSent`).
- **Скупка отваров**, которые не пьют, а продают (шнапс, самогон — `BrewEffect.Sellable`): все
  бутылки разом, каждая по своей цене (`InnkeeperState.worth`).
- **«Письмо Марисе»**, первый шаг: что Трактирщик знает об адресате (`AskMarisa`).
- **Вернуться** (`BackFromInnkeeper`) → `Goto(Tavern)`.

> Начисление опыта с прокачкой уровней живёт **только** в `Hero.gainExp` (`copy(exp/lvl/upgradePoints)`, кап `Hero.MaxLevel`, `Hero.PointsPerLevel` очков за уровень); через него начисляют все — бой, доска заданий, задания и поручения горожан (`NpcQuestLog`, `DailyDialog`), — дублирования цикла нет.

### Зелья Фета

В лавке Фета, кроме артефактов, — три зелья (`FetPotion`) по `FetShopState.PotionPriceDoubloons` = 100
дублонов. Их выпивают сразу при покупке; бесполезное (`FetPotion.useful`) не продаётся.

- **Зелье застоя** ставит `Hero.expFrozen` (колонка `heroes.exp_frozen`). Пока он стоит, опыт не
  идёт ниоткуда: `gainExp` возвращает героя как был. Начисления зовут `Hero.expFrom`, поэтому игроку
  показывают то, что пришло на самом деле, — «+0». Это бой, задания и поручения горожан, доска,
  стройка и пещера. Штраф опыта за смерть остаётся. «Персонаж» пишет «❄ Опыт остановлен».
- **Зелье движения** снимает `expFrozen`.
- **Зелье забвения** — `Hero.respec`: характеристики возвращаются к старту (`Hero.StartBaseStats` —
  по 4), вложенное (`Hero.spentPoints`) уходит в свободные очки. Раса, зелья Густаво (`statBoosts`),
  достижения и наборы в `baseStats` не хранятся — их прибавляют сверху при подсчёте
  (`effectiveBaseStats`), поэтому сброс их не трогает и в свободные очки они не попадают. Здоровье и
  энергия выше нового потолка срезаются до него.

**Зажим снизу.** Боевые статы зажаты в `.max(1L)` — атака, защита, точность, уклонение, сосредоточение и `effectiveMaxHp` не могут упасть ниже 1, какие бы травмы ни накопились (броня — исключение, `.max(0L)`, т.к. 0 без экипировки легитимен). Базовые характеристики (`effectiveBaseStats`) тоже зажаты в 1; ловкость штрафа от травм не имеет. Расчёт «потолка» без травм — `Hero.maxFightStats` / сырые `baseStats` (общий приватный `fightStatsWith(penalties)`).

**Отображение на экране «Персонаж».** `Hero.getInfo` показывает стат как `текущее/максимум`, если травма уронила его ниже потолка (напр. `СИЛ 5/10`, `Атк 5/10`), и просто числом, если дебаффа нет. HP (`❤`) и броня (`🧥 Броня`) показываются как `текущее/эффективный максимум` всегда (броня — `min(current, effectiveMaxArmor)/effectiveMaxArmor`). Хелпер `Hero.withMax(cur, max)`.

### Дроп предметов

Каждый предмет в **инвентаре** (не в слотах экипировки) имеет **25% независимый шанс быть потерянным**.

- Реализовано в `DeathState.dropItems`: `Random.nextIntBetween(0, 4)`, дроп при `roll == 0`
- Потерянный предмет удаляется из инвентаря (`InventoryRepository.removeItem`)
- Игроку показывается сообщение: **«{monsterName} забрал(а) {itemName} себе в качестве трофея.»**
- Имя монстра читается из `ActiveBattle` (через `heroDao.readActiveBattle`) **до** вызова `heroDao.clearActiveBattle`; если активной битвы нет — fallback `"Монстр"`

### Отдых после смерти

Время мёртвого режима растёт по **уровню героя** и асимптотически стремится к 90 минутам, не достигая их:

```
deathTimeMinutes = 90 − 89 × exp(−k × (lvl − 1))      // k = DeathState.RestGrowthK = 0.01
restDurationMs   = deathTimeMinutes × 60 000
```

- На 1 уровне — ровно **1 минута** (`90 − 89×exp(0) = 1`).
- С ростом уровня время монотонно увеличивается, но строго меньше 90 минут (асимптота).
- `k` (`DeathState.RestGrowthK`) задаёт скорость роста.

Записывается в `scene_data`; `RestState` читает это значение и блокирует выход до истечения времени.

## 19. Инвентарь и экипировка

### Слоты экипировки

`Equipment` содержит 15 именованных слотов:

| Слот | Поле | Тип |
|---|---|---|
| Шлем | `helmet` | `Helmet` |
| Наплечники | `shoulderPads` | `ShoulderPads` |
| Нагрудник | `chestPlate` | `ChestPlate` |
| Браслеты | `bracelets` | `Bracelets` |
| Перчатки | `gloves` | `Gloves` |
| Штаны | `pants` | `Pants` |
| Сапоги | `boots` | `Boots` |
| Амулет | `amulet` | `Amulet` |
| Кольцо 1 | `firstRing` | `Ring` |
| Кольцо 2 | `secondRing` | `Ring` |
| Пояс | `belt` | `Belt` |
| Фляга | `flask` | `Flask` |
| Правая рука | `weapon` | `Weapon` |
| Левая рука | `leftHand` | `Weapon` (одноручное) |
| Доп. оружие | `additionalWeapon` | `AdditionalWeapon` |

Экипировка хранится как JSONB в колонке `heroes.equipment`.

### Два слота под кольца (авто-логика)

Кольца — пара слотов, как и руки (см. ниже; в руки встаёт оружие или щит). Логика надевания в `InventoryState`:

- `firstRing` свободен → кольцо идёт в `firstRing`
- `firstRing` занят, `secondRing` свободен → кольцо идёт в `secondRing`
- Оба заняты → кольцо идёт в `secondRing`, старое кольцо из `secondRing` возвращается в инвентарь

Игрок явно управляет кольцами через экран снаряжения (`EquipmentState`), где `firstRing` и `secondRing` — отдельные слоты с кнопкой «Снять».

### Две руки и хват оружия

У оружия есть хват (`Item.grip`, `Grip`): одноручное, двуручное, стрелковое
(лук, арбалет) или парирующий кинжал. Одноручное или в обе руки — поровну
(`ItemGenerator.applyGrip`). Одноручное — поровну меч, топор, кинжал, копьё или
парирующий кинжал: кинжал выходит каждым десятым оружием. В обе — поровну меч,
топор, копьё, лук или арбалет: лук или арбалет выходит каждым пятым. Так — в дропе,
магазине, кубе, вещах наборов. Числа — в `GripRates`.

- **Одноручное** несёт 60% каждого своего стата (итог, вместе с обязательной
  прибавкой к атаке). Пара одноручных — 120%.
- **Двуручное** — все 100%, и гнёзд у него на одно больше, чем по таблице оружия,
  но не больше четырёх. Серое, белое и зелёное гнёзд не носит вовсе.
- В имени двуручного слово хвата стоит перед существительным и согласуется по
  роду: «🔵 Хороший Двуручный Меч Рыцаря», «Двуручное Копьё». Двуручное — только
  меч, топор и копьё: кинжал всегда одноручный. Пересборка в кубе с прежним
  именем держит прежний хват.

Надевание (`InventoryState.equip` → `wield`) — по схеме колец:

- одноручное встаёт в свободную руку, сперва в правую; обе заняты одноручным —
  экран выбора руки (`EquipHand`, `Equipment.handsFull`);
- двуручное встаёт в правую (`weapon`) и снимает всё, что было в обеих; левая
  остаётся пустой и показывается «занята двуручным» (`Equipment.leftBusy`);
- одноручное поверх двуручного снимает двуручное;
- двуручное поверх двух одноручных кладёт в сумку на вещь больше, чем забирает:
  в полную сумку его не надеть (`InventoryState.equipBlock`, `inventory.handsNoRoom`).

Обе руки считаются в наборы — вещей набора можно надеть тринадцать, но счёт
(`Equipment.setCounts`) упирается в двенадцать: полный набор по-прежнему 12.
Навыки берутся с оружия в обеих руках, «без оружия» — когда пусты обе
(`Equipment.unarmed`), камни обеих рук — в «оружейной» грани и в ссоре с пылью.

Старые записи: в снаряжении без `leftHand` левая рука пуста, а прежнее оружие
остаётся в правой; оружие без хвата — одноручное со статами как были.

### Лук и арбалет

Стрелковое оружие (`Grip.Bow`, `Grip.Crossbow`) — двуручное со всеми 100% статов
и гнездом сверх таблицы, как у двуручного. Слова «Двуручный» в имени нет: «🔵
Хороший Лук Стрелка». Пока лук и арбалет ничем не отличаются.

- **Дальность.** Герой бьёт на `GripRates.RangedReach` = 3 места в обе стороны:
  с четвёртого места — по местам 1–7 (`GroupState.targetsWithin`,
  `BattleState.heroReach`). Прочее оружие — только соседей (`GroupState.Reach`).
  Удар по дальней цели идёт так же, как по соседу, — через подмену в полях.
- **Вблизи слабее.** По тому, кто напротив, и по соседям стрелковое бьёт на
  `GripRates.RangedClosePenaltyPct` = 20% слабее (`BattleState.rangedCloseMod`).
  В бою один на один цель вблизи; на арене — смотря как стоят бойцы.
- **Умения** оружия целятся и слабеют вблизи так же, как удар
  (`BattleState.skillReach`). Умения нагрудника — Таран и «Отбросить», удары телом
  и щитом — бьют только вблизи и без штрафа. Задевающие остальных (дуга
  Размашистого, Вихрь, Веерный порез, Боевой клич) задевают их вокруг героя или цели,
  как и раньше.
- Мобы и союзники бьют соседей, башни — любое место. Исключение — эльфы: они стрелки,
  бьют на 3 места в обе стороны и сами ближе не подходят. Орки быстры и за раунд
  проходят 2 места. Оба правила — в `RaceTactics` (`reach`, `speed`).

**Свои умения** (`Skill.rangedSkills`): на лук и арбалет выпадают только они, на прочее
оружие — прежние (`Skill.weaponSkills`). Это руны, но умения стрелка применяются, лишь
когда в руках лук или арбалет, а прочие умения оружия — лишь без них
(`Skill.usableWith`, фильтр в `Hero.activeSkillSlots`): и с вещи, и с клейма. Умения
нагрудника и щита с кинжалом от оружия не зависят. Бьют умения стрелка на всю
дальность оружия (`BattleState.skillReach`) — числа «три» в них нет.
- **Пригвоздить** (`Effect.Pin`) — урон, срезанный защитой, и цель два раунда не сходит
  с места.
- **Заградительный залп** (`Effect.Volley`) — урон цели и каждому врагу в пределах
  дальности, срезанный защитой каждого; раунд никто из задетых не шагает.
- **Отскок** (`Effect.Leap`) — герой отпрыгивает по своему ряду и стреляет уже с нового
  места (`GroupState.leapSpot`). Прыжок — на `BattleState.displacement` мест
  (дальность − 1). Место — без союзника, напротив пусто, и цель остаётся в
  досягаемости. Из таких — где рядом меньше врагов. Некуда — выстрел с места.
- **Отбрасывающий выстрел** (`Effect.Push`) — урон, и выживший отлетает от героя по
  своему ряду на те же «дальность − 1» мест (`SoloPveBattle.pushActive`). Живых он не
  перелетает и встаёт перед ними. Минибоссов и сооружения не сдвинуть. Пара рвётся,
  добивающий удар идёт по цели на новом месте (`nextAt` в `skillHit`) — в этом раунде
  лук достаёт её, даже если она улетела дальше дальности; дальше — как обычно.

**Места на арене.** У каждого бойца своё место в своём ряду (`ArenaSide.pos`), в
начале боя — друг напротив друга. В зеркале боя герой стоит на своём месте, соперник —
на своём (`ArenaBattle.assemble`), и строй виден всегда, даже вплотную. Сам никто не
ходит: соперник двигается только своим ходом (`pullFreeStep`, `closeIn` и перемешивание
на арене молчат, сородичи не прибегают — `noKin`). «Переместиться» и «Отскок»
переставляют героя, «Отбрасывающий выстрел» — соперника. «Пригвоздить» и «Залп»
запирают соперника на столько его ходов (`ArenaSide.rooted` →
`BattleEffects.heroRootedTurns`): не шагнуть, не отпрыгнуть, Тараном не сдвинуться.
Что ход сделал с местами, соперник читает в сводке. Просроченный ход — удар, если есть
кого бить, иначе ожидание.

**Режимы арены** (`ArenaMode`) выбираются первыми в меню арены. Один на один отряд
остаётся за оградой. В групповом бою каждый выходит со своим отрядом
(`ArenaBattle.withSquad`), и встают так же, как в лабиринте (`Squad.compact`). Очередь у
каждого режима своя (`ArenaDao.waiting(limit, mode)`); в списке групповых видно, сколько
бойцов выйдет с ждущим. Запись по коду ведёт в режим записи. Ждал в одном режиме, нажал
другой — запись переходит туда, код прежний.

**Союзники на песке.** У стороны свои союзники (`ArenaSide.allies`), у каждого — свой номер
на весь бой:
- крысы из-под ног (набор «Крыса»): на старте при пороге 12 (`ArenaBattle.withStartingRat`),
  посреди боя при пороге 6;
- в групповом бою — отряд.

В своём зеркале они союзники и бьются в ход героя (`allyPhase`). В чужом — «мобы» со
своим номером (`MonsterSlot.arenaUnit`, сам соперник — `SoloPveBattle.ArenaHeroUnit`).
Их можно бить, а урон, место и смерть возвращаются их стороне
(`ArenaBattle.foeAfterTurn`).
- Чужие бойцы в зеркале не ходят: `sideMobsPhase` на арене молчит.
- Раны на чужих бойцах тикают в конце хода того, кто их наложил (`arenaWounds`). Что
  сторона наложила на чужих союзников, хранится в `ArenaSide.marks`.
- Сторона падает, только когда пали все. Павший герой лежит (`group.heroDown`), а его
  отряд в его ход бьётся сам (`downTurn`). Победитель, если лежал, встаёт с 1 HP.
- Щит и кинжал держит только сам соперник (`foeShieldUp`, `foeCounterPower`).
- «Некромант» на арене никого не поднимает.
- Отряд в «Отряде» арена не трогает: на песке — копия.

«Не сходит с места» — `BattleEffects.monsterRootedTurns` (с запасом в один тик, как
`monsterSkillBlockedTurns`): такой моб не идёт к герою (`closeIn`,
`stepActiveTowardsHero`), не уходит к союзнику над лежащим героем и стоит при
перемешивании. Сквозь него не проходят, как сквозь башню. Некромант пригвождённым за
спины своих не уходит. Отбросить его можно: это не его шаг. В строю у имени — 📌.

### Щит и Блок

Щит (`ItemType.Shield`) держат в руке, как одноручное, — в любую руку и в любом
сочетании: щит и меч, два щита, щит и кинжал. Но щит не оружие: с двумя щитами герой
бьёт голыми руками (`Equipment.unarmed`, половина урона), а камни в щите — броневые.

- Падает так же часто, как оружие, в «тяжёлом» профиле (броня и защита). Виды —
  только имя: Круглый Щит, Треугольный Щит, Баклер, Башенный Щит, Костяной Щит.
- Защита у щита всегда есть: `ShieldRates.DefencePerLvl` = 3 × уровень вещи, поверх
  случайных статов. Атаки нет, пассивки нет. Гнёзд — по таблице оружия, но не
  больше `ShieldRates.MaxSockets` = 2.
- Умение у щита одно и всегда своё — **Блок** (`Skill.Block`, `ItemDetails.HandSkill`).
  Это умение «оружия», но не руна: Казимир его не снимает, рунных камней на него нет
  (`Skill.handSkills`, `RuneStone.all`).
- **Блок**: перезарядка 2, готов с начала боя, стоит 10 + уровень/2 энергии (и общая
  надбавка). Это бонусное действие раунда (см. «Бонусное действие») — ход на нём не
  кончается: после него можно ударить или взять умение. До конца раунда обычные атаки и
  умения врагов по герою (моб напротив, соседи сбоку, приёмы боссов) режутся на
  процент щита — уже после защиты (`BattleState.shieldCut`). Процент — по редкости
  лучшего щита в руках (`ShieldRates.blockPct`, `Equipment.blockPct`): серый и белый
  — 50%, дальше +5% за каждую редкость (фиолетовая и пурпурная — разные), легендарный
  — 75%. Описание Блока называет число (`{block}` в `Skill.describe`): на карточке щита —
  этого щита, в списке умений — лучшего надетого. Щит поднят, пока
  `SoloPveBattle.heroBlockPct` > 0; он опускается первым действием героя в следующем
  раунде.
- Кнопка Блока стоит в ряду действий, справа от «Атаки».
- **Арена.** Поднятый щит запоминается на стороне (`ArenaSide.shieldUp`, его
  собирает `ArenaBattle.harvest`) и в зеркале соперника становится
  `SoloPveBattle.monsterBlockPct` — по его щиту: удар и умение соперника в его ходе
  режутся так же.

### Парирующий кинжал и Контрудар

Парирующий кинжал (`Grip.Parrying`) — одноручное оружие, в любую руку. Несёт
`GripRates.ParryingPct` = 40% статов — слабее даже обычного одноручного. Имя —
«🔵 Хороший Парирующий Кинжал Рыцаря», гнёзд — по таблице оружия, но не больше
`GripRates.ParryingMaxSockets` = 2.

- Умение у кинжала одно и всегда своё — **Контрудар** (`Skill.Counterstrike`,
  `ItemDetails.HandSkill`), как и Блок, не руна.
- Перезарядка 3, готов с начала боя, стоит 13 + уровень/2 энергии (и общая
  надбавка). Как и Блок — бонусное действие раунда: ход на нём не кончается.
- До конца раунда кинжал наизготовку (`SoloPveBattle.heroCounterReady`): первый
  удар врага, от которого герой увернулся, — моба напротив или соседа сбоку, —
  тут же получает ответ: обычный удар героя без промаха (`playerStrike`,
  `sureHit`). Один ответ за раунд. Стойка снимается первым действием героя в следующем
  раунде.
- Кнопка Контрудара стоит в ряду действий, справа от «Атаки».
- **Арена.** Стойка запоминается на стороне (`ArenaSide.counterUp`). В зеркале
  соперника она становится силой ответного удара (`SoloPveBattle.monsterCounterPower`,
  `ArenaBattle.counterPower` — та же формула удара героя, но без проков: ни ядов,
  ни огня, ни стихий). Промахнулся соперник — и в своём же ходе получает этот удар
  с обычным разбросом, срезанный его защитой и бронёй (`BattleState.arenaCounter`).

### Бонусное действие

За раунд у героя одно бонусное действие (`SoloPveBattle.consumableUsedThisRound`): глоток
или бросок с пояса, Блок или Контрудар — что-то одно (`BattleState.bonusAction`). Оно не
кончает ход: после него можно ударить, взять умение и так далее. «Быстрые руки» с шансом
25% его не тратят — и для пояса, и для Блока с Контрударом. Потрачено — пояс, Блок и
Контрудар отвечают «бонусное действие уже потрачено», а их кнопки краснеют.

- `SoloPveBattle.midRound` — раунд героя ещё идёт: прошлое действие его не кончило. Щит и
  стойку прошлого раунда снимает только первое действие нового раунда
  (`BattleState.resolveLoaded`), поэтому поднятый посреди раунда щит держится, пока
  мобы бьют в его конце.
- `SoloPveBattle.bonusSlots` — умения, взятые бонусным действием в этом раунде: в конце
  раунда их перезарядка не тикает (`tickBuffs`), как у умения, которым раунд кончился.
  Перезарядка у Блока и Контрудара поэтому прежняя.

**Одинаковые умения не складываются**: если одно и то же умение есть на двух вещах
(два одинаковых меча, два щита), у героя одна кнопка и одна перезарядка, как будто
умение одно (`Hero.activeSkillSlots`).

### Вместимость сумки и фидбэк при получении предмета

Вместимость инвентаря — `Inventory.DefaultCapacity = 20` слотов (единая константа; `InventoryDaoLive.create` берёт её при создании сумки). `Inventory.freeSlots = max(maxItems − items, 0)`.

**При получении предмета любым способом** (лут `LootState`, найденный предмет `FoundItemState`, покупка `MerchantState`, снятие экипировки `EquipmentState`) к сообщению добавляется строка «🎒 Свободных слотов в сумке: {free}/{max}» (`common.freeSlots`). Общий хелпер — `InventoryFeedback.freeSlotsLine`.

**При переполнении** (предмет не влез) показывается единое сообщение `common.inventoryFull` — «❌ Сумка странника переполнена трофеями прошлых битв. Новому предмету не нашлось места.» (раньше у каждого экрана был свой текст: `foundItem.inventoryFull`/`merchant.inventoryFull`/`equipment.inventoryFull`/`loot.itemLost` — удалены). Исключение — снятие предмета в `EquipmentState`: там своё сообщение `equipment.unequipInventoryFull` («Инвентарь переполнен, надо бы очистить место прежде чем снять с себя.»), потому что смысл действия другой (снимаешь то, что уже носишь, а не пытаешься подобрать новое).

### «Забрать и надеть»

Только что полученную вещь можно сразу надеть — в пустой слот или вместо надетой:

| Где | Пустой слот | Вместо надетой |
|---|---|---|
| добыча (`LootState`) | «Забрать и надеть» (`TakeWear`) — всё подходящее разом | «Надеть: …» (`TakeSwap`) — по кнопке на вещь |
| находка (`FoundItemState`) | «Забрать и надеть» (`TakeWearItem`) | та же кнопка |
| Ришелье (`MerchantState`) | «Да, и надеть» (`ConfirmBuyWear`) | та же кнопка |

Новая вещь в сумку не заходит, поэтому в пустой слот её можно надеть и при полной сумке.
Снятое при замене уходит в сумку. Общий код — `service/state/TakeAndEquip`:

- `fits(hero, item)` — встаёт ли вещь в пустой слот: её надевают (не фляга, не роза),
  уровень не выше героя, слот свободен. У кольца — любой из двух, у одноручного и щита —
  свободная рука (и в другой не двуручное), у двуручного — обе руки. `replaces` — то же,
  но пустого слота нет; `canWear` — одно из двух.
- `pick(hero, items)` — что из добычи надеть в пустые слоты: лучшие первыми (редкость,
  потом уровень). Из двух шлемов надевается более редкий, второй уходит в сумку.
- `noRoom(hero, inv, item, slot)` — хватит ли сумке места под снятое: по месту на каждую
  снятую вещь (двуручное поверх двух одноручных снимает обе), с учётом «Тайника».
  Не хватает — не надеваем: `common.swapNoRoom` или `equipment.stashBlocked`, вещь
  остаётся на экране.
- `wear(...)` — снаряжение и статы через `InventoryState.equip`, снятое — в сумку, места
  от «Тайника» (новый — до того, как снятое ляжет в сумку, потеря последнего — после).
  На добыче надеваем до того, как остальное ляжет в сумку. Достижение за набор
  (`QuestSupport.grantFullSets`) вызывающий выдаёт сам, после своей строки о получении.

Оба кольца или обе руки заняты — сперва спрашиваем, что снять: экран `SlotChoice` общий с
инвентарём. Его кнопки — та же кнопка надевания с номером слота (`slot`: 1 и 2), «Назад»
(`common.back`) возвращает к добыче, находке или лавке. Кнопка «Надеть: …» несёт номер и
имя вещи: со старого экрана, где добыча уже другая, она только показывает превью. Если
надеть уже нельзя, вещь просто ложится в сумку. У каравана и на аукционе этих кнопок нет.

### Пояс: содержимое за героем (`BeltContents`)

Фляги, пыль, отвары, святая вода и розы лежат в ячейках надетого пояса (`ItemDetails.Belt`,
ячеек по редкости — `Belt.capacityFor`). Бой, пополнение у Густаво и «На пояс» работают с ними
как раньше. Новое правило: содержимое принадлежит герою, и с героя пояс не уходит с вещами
внутри.
- **Смена пояса** (`BeltContents.swap`, внутри `InventoryState.equipWith` — общий путь для
  инвентаря, экрана снаряжения и «Забрать и надеть»). Содержимое переезжает в новый пояс:
  полные ячейки первыми, пустые последними, следом то, что уже лежало в новом. Что не вошло по
  ёмкости — вещами в сумку (`Equipped.spilled`); лишние пустые ячейки пропадают. Старый пояс
  уходит пустым. Не хватает места в сумке — пояс не надевается (`inventory.beltNoRoom`).
- **Снятие пояса** (`BeltContents.strip`, экран снаряжения). Пояс уходит пустым, содержимое —
  вещами в сумку. Места нужно на сам пояс и на всё, что место занимает (пыль невесома); не
  хватает — пояс не снимается.
- **«На пояс» при полном поясе** (`InventoryState.beltSwapScreen`). Кнопка на каждую ячейку:
  «Вместо: …». Снятое уходит в сумку вещью, пустой ячейке возвращать нечего. Сумке должно
  хватить места: новая вещь освобождает своё, снятая занимает; пыли — не больше сотни горстей.

Вещь из ячейки — `BeltContents.item`: фляга и роза — со своими зарядами, пустая фляга остаётся
флягой. Перед сумкой такие вещи сохраняются (`BeltContents.persist`): у свежей вещи id ещё нет
(-1), а сумка различает вещи по id — две такие слились бы в одну. Это же правило теперь и у
кнопки «Вынуть» на экране снаряжения.

### «Персонаж» как модальный экран (`HeroStatsState`)

«Персонаж» открывается **из любой локации-хаба** (Лабиринт, Город, Таверна, Ришелье, Доска заданий, Трактирщик) — кнопкой `OpenCharacter`. Реализация — «вариант со слотом возврата» (depth-1), а не нав-стек в ядре:

- Единая точка входа `CharacterMenu.open(heroDao, userId, from)` пишет локацию-источник в `heroes.return_state` (`StateType`, nullable) и делает `Goto(HeroStats)`.
- `HeroStatsState` `Back` читает `return_state` (по умолчанию `Dungeon`) и возвращает туда же; `targetStates` перечисляет все хабы-источники (нужно валидатору графа).
- Глубина 1 достаточна, потому что внутри «Персонажа» граф фиксированный: `Inventory`/`Equipment` всегда возвращаются в `HeroStats` (`BackFromInventory`/`BackFromEquip` → `Goto(HeroStats)`), а сам слот пишется только в момент открытия «Персонажа» и серийно переиспользуется. Это намеренно: переписывать роутинг под общий нав-стек не стали (YAGNI), апгрейд слот→стек позже локальный.
- `Inventory`/`Equipment` достижимы **только** через «Персонаж» — прямой шорткат «Лабиринт → Инвентарь» убран.

### Экран инвентаря (`InventoryState`)

Пагинация по предметам в инвентаре. На каждом предмете:
- Кнопки «Надеть», «Выбросить», навигация, «Выйти»
- Для колец в шапке показываются оба текущих слота («Слот 1: X / Слот 2: свободен»)
- Шапка включает количество серебра (`🪙 N`)
- Надевание: `updateEquipmentAndFightStats`, вытесненный предмет → `addItem` в инвентарь

### Экран снаряжения (`EquipmentState`)

Пагинация по 14 слотам (`EquipmentState.slots`). Для каждого:
- Показывает имя слота, название предмета и его статы, или «Пусто»
- Кнопка «🔓 Снять» видима только если слот занят
- Снятие: `addItem` → если инвентарь полон, показывает ошибку и предмет остаётся
- После снятия пересчитываются `fightStats` через `InventoryState.applyDelta`
- Страница сохраняется в `heroes.scene_data` (аналогично `InventoryState`)

Доступ: `HeroStatsState` → кнопка «Снаряжение» → `StateType.Equipment`.

### Серебро

Отображается в шапке экрана инвентаря (`📦 Инвентарь (N/M) | 🪙 G`) и в экране пустого инвентаря. В экране снаряжения и на экране найденного предмета (`FoundItemState`) серебро не показывается.

### Распределение очков характеристик (`HeroStatsState`)

Кнопка «Распределить характеристики» появляется только при `upgradePoints > 0`.

После нажатия открывается меню с четырьмя кнопками (+СИЛ / +ТЕЛО / +ЛОВ / +ИНТ) и кнопкой «Назад». Применение одного очка **не закрывает меню**: `applyUpgrade` сохраняет изменение, показывает подтверждение («Характеристика улучшена!»), затем вызывает `showUpgradeScreen` повторно. Та перечитывает героя и:
- если очки ещё есть — показывает меню снова с обновлённым счётчиком;
- если очки исчерпаны — показывает «Нет свободных очков» и кнопки стандартной навигации.

Игрок выходит явно через «Назад» или автоматически когда очки заканчиваются.

## 20. Дроп с врагов

> **Статус: ✅ реализовано.** При победе с моба падает лут из общего пула. «Что выпало» считает чистое ядро `LootGenerator` (`generator/loot`, явный `Rng`); начисление и показ — shell (`BattleState.victory` → промежуточный `LootState`). Это functional core / imperative shell (§3).

### Поток

1. `BattleState.victory` начисляет опыт/уровень (как раньше), затем катает лут `LootGenerator.roll(монстр.rarity, монстр.race, killLevel, Rng(seed))`. `killLevel = hero.dungeonLevel`.
2. Непросохранённые предметы (id = −1) + список серебряных выпадений кладутся в `scene_data` (`LootState.LootData`), `victory` возвращает `StateType.Loot`.
3. `LootState.enter` («осматривая добычу, вы находите следующее:») **сразу начисляет серебро** (серебро забирается всегда, без выбора). Если выпали и предметы — показывает превью (серебро + предметы) и двумя **inline-кнопками внутри сообщения** спрашивает «Забрать»/«Оставить» по предметам (`Screen(text, choices, inline = true)`). Если что-то встаёт в пустой слот, под «Забрать» идёт «Забрать и надеть», а под ней — «Надеть: …» на каждую вещь, которая встанет вместо надетой (см. «Забрать и надеть»).
4. **«Забрать»** (`Take`) — персистит каждый предмет (реальный id) и кладёт в инвентарь, пишет `loot_claimed`, показывает итог → `Dungeon`. Полный инвентарь → предмет **теряется**, в списке строка «{name} — Инвентарь переполнен». Серебро не трогает (уже забрано в `enter`).
5. **«Оставить»** (`Leave`) — предметы выбрасываются (серебро остаётся забранным), пишет `loot_left` → `Dungeon`.
6. Только серебро / пустой лут → нет выбора: показывается «вы не находите ничего ценного» или список серебра с кнопкой «Продолжить» (`Continue`) → `Dungeon`.

**Серебро теперь не гарантировано** — старая постоянная награда `silverGained` убрана из `victory`, серебро падает только как категория лута (решение игрока, ответ 3).

### Сколько слотов дропа катаем (по тиру моба)

Каждый слот срабатывает независимо со своим шансом (`LootGenerator.dropChances`).

| Тир | 1-й слот | 2-й | 3-й |
|---|---|---|---|
| Обычный | 30% | — | — |
| Необычный | 60% | 30% | — |
| Редкий | 100% | 60% | — |
| Мифический | 100% | 60% | — |
| Легендарный | 100% | 100% | 60% |

**Без повторов категории** (ответ 4): уже выпавшая категория исключается из следующих слотов.

### Веса категорий (если слот сработал)

Один взвешенный бросок 0–100. Веса **одинаковы для всех тиров** и в сумме дают 100 — на первом слоте «пусто» нет, слот всегда что-то роняет. На последующих слотах уже выпавшая категория исключается (без повторов, ответ 4), суммарный вес активных категорий падает, и появляется доля «пусто» (например, на 3-м слоте легендарного, когда экипировка и трофей уже выпали, остаётся только серебро 26%, остальные 74% — «пусто»).

| Категория | Вес |
|---|---|
| Экипировка | 35 |
| Трофей | 39 |
| Груда серебра | 26 |

«Груда серебра» даёт серебро по формуле `killLevel×4 ±20%` (мин 1).

### Редкость выпавшей экипировки (по тиру моба)

Маппинг рангов: серая→`Gray`, белая→`White`, зелёная→`Green`, синяя→`Blue`, фиолетовая→`Purple`, пурпурная→`Violet`, легендарная→`Orange`. Веса в `LootGenerator.gearRarityWeights` хранятся в долях `1/1 000 000` (фракции из исходного спека), суммы доведены до 100% (числовые ошибки спека исправлены: Common Green 16.4995; Rare/Myth/Leg добирают недостающие 0.5% в Green).

| Редкость | Обыч | Необ | Редк/Миф | Лег |
|---|---|---|---|---|
| серая (Gray) | 45 | 30 | 20 | 0 |
| белая (White) | 35 | 45 | 40 | 20 |
| зелёная (Green) | 16.4995 | 19.4995 | 31.0 | 31.0 |
| синяя (Blue) | 2 | 3 | 5 | 25 |
| фиолетовая (Purple) | 1 | 2 | 3 | 13 |
| пурпурная (Violet) | 0.5 | 0.5 | 0.5 | 9.5 |
| легендарная (Orange) | 0.0005 | 0.0005 | 0.5 | 1.5 |

**Уровень** выпавшей экипировки — текущий разброс `−0..6` из `ItemGenerator` (ответ 5): редкость передаётся в `ItemGenerator.createItem(killLevel, rarity, rng)`, который сам применяет разброс уровня.

### Трофеи

Хранятся **как обычный предмет в инвентаре** (ответ 1): `ItemType.Trophy`, без статов, `lvl = killLevel`; раса и вид трофея — в `details` (`ItemDetails.Trophy(race, kind, coef)`). Имя — `<тип> (<раса>)` (например, `Талисман (Эльф)`). Уровень в имя **не** включается — он показывается отдельно как `Ур.<lvl>` при выводе списка (`LootState`/`InventoryState`), чтобы не дублировать. Трофей **не экипируется** (нет в `attackItems`/`defenceItems`; `InventoryState` блокирует «Надеть» сообщением `inventory.notEquippable`). «Коэффициент трофея» — коэффициент его вида (`TrophyKind.coef`: Реликвия 4, Талисман 2, Голова 1, Мешок 0.5; у клыка Белого волка он свой и лежит на предмете — `ItemDetails.Trophy.coefValue`). По формуле `ceil(5 + Ур.трофея × коэффициент)` Гильдия платит репутацией в обменнике трофеев (`TrophyKind.reputationFor`), а доска — опытом за трофейное задание (`BoardRates.trophyExp`, см. «Доска заданий»).

Тип трофея катается по весам (`LootGenerator.trophyWeights`, суммы = 100):

| Тип | Обыч | Необ | Редк | Миф | Лег |
|---|---|---|---|---|---|
| Реликвия | 1 | 5 | 15 | 15 | 25 |
| Талисман | 9 | 15 | 20 | 25 | 45 |
| Голова | 20 | 20 | 25 | 30 | 20 |
| Мешок с пожитками | 70 | 60 | 40 | 30 | 10 |

### Ключевые файлы

- `generator/loot/LootGenerator.scala` — чистое ядро (`roll`, `LootDrop`, все таблицы).
- `service/state/states/LootState.scala` — промежуточный экран добычи (`LootData` в `scene_data`).
- `service/state/states/battle/BattleState.scala` — `victory` катает лут и уходит в `Loot`.
- `model/item/ItemDetails.scala` (`Trophy`: раса, вид, свой коэффициент), `model/item/TrophyKind.scala`, `model/item/ItemType.scala` (`Trophy`), `model/state/StateType.scala` (`Loot`).

Решение игрока пишется в журнал: `loot_claimed` (забрал — серебро + имена предметов) или `loot_left` (оставил), как и `FoundItemState`.

## 21. Уличные торговцы (магазин)

В городе (`GlobalMapState`) есть кнопка «Уличные торговцы» → подменю с «Торговец Ришелье» (→ `StateType.Merchant`) и «Назад». `MerchantState` — лавка одного торговца.

### Сток (durable, фиксированный)

Торговец держит **3 предмета снаряжения**, зафиксированных до явного обновления. Сток durable — отдельная колонка `heroes.merchant_data JSONB` (не `scene_data`, иначе бой/подземелье затёрли бы его), читается/пишется через `HeroDao.read/writeMerchantData`.

- Модель: `MerchantData(items: List[MerchantItem], refreshedAt: Long)`, `MerchantItem(item, price, bought)`.
- Генерация (при первом входе или обновлении): каждый предмет катается **ровно на уровень героя без разброса** (`ItemGenerator.createItemAtLevel`, в отличие от `createItem` с разбросом −0..6).
- Редкость: **Белая 20% · Зелёная 50% · Синяя 30%**.
- Цена покупки: `(lvl_героя + 20) × 4 × R(редкость) ±20%`, где `R = Rarity.factorR` (White 3, Green 4, Blue 6, Purple 8). `±20%` фиксируется при генерации и хранится в стоке (показанная цена = списываемая).

### Кнопки (6)

1–3. **Купить N** (только для некупленных): подтверждение «Вы уверены что хотите купить предмет {name} за {N} серебра?» → `Да`/`Нет` (если товар встаёт в пустой слот, между ними — «Да, и надеть», см. «Забрать и надеть»). На `Да`: хватает серебра → списываем, кладём в инвентарь (persist реального id), помечаем `bought` (кнопка исчезает), «Вы купили предмет {name}». Не хватает → «Ага конечно, как будет достаточно звонких монет тогда и продам.». Инвентарь полон → предмет не выдаётся, серебро не списывается.
4. **Обновить товар** — перекатывает сток, **не чаще раза в час** (`now − refreshedAt ≥ 1ч`, `RefreshCooldownMs`); иначе сообщение с остатком минут. До обновления предметы зафиксированы.
5. **Продать снаряжение** — пагинация по инвентарю (как `InventoryState`, но кнопка «Продать» вместо «Выбросить»), страница в `scene_data` (`SellPage`). Цена выкупа: `(lvl_снаряжения + 5) × 1.2 × R(редкость)` (без `±20%`; дешевле покупки). На продажу: убираем из инвентаря, начисляем серебро.
6. **Назад** — `Goto GlobalMap`.

Все под-экраны (меню/подтверждение/продажа) — внутри одного `StateType.Merchant`, маршрутизация `Branch`; индекс предмета передаётся в payload кнопки (`idx`).

## 22. Глоссарий

- **Сцена (Scene/State)** — узел графа: что показать и какие переходы. Бывает нарратив, выбор, эффект.
- **Бит (Beat)** — одна реплика линейного нарратива: текст + кнопка «дальше».
- **Эффект (Effect)** — код, выполняемый по кнопке: оркестрирует ядро/сервисы и выбирает следующую сцену.
- **Цель (Target)** — куда ведёт кнопка: `Goto` (переход-данные) или `Run` (эффект-код).
- **Live scene state / scratchpad** — переходное состояние текущей сцены (блоб на герое).
- **Durable game state** — постоянные данные игрока (статы, инвентарь).
- **Журнал (event_log)** — append-only лог фактов для дебага/аналитики.
- **Functional core / imperative shell** — чистое доменное ядро vs эффект-оркестратор.
- **Renderer / Adapter** — порт показа `Screen` и его реализация под платформу (ВК/Telegram/тест).
- **`EquipmentState.Slot`** — описатель слота экипировки: имя, геттер `get: Equipment => Item`, сеттер `clear: Equipment => Equipment`.
- **`merchant_data`** — durable JSONB-колонка на герое со стоком торговца (3 фиксированных предмета + `refreshedAt`); переживает переходы сцен, в отличие от `scene_data`.
- **trace_id** — идентификатор, связывающий записи журнала одного действия.
